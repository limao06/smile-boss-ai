# 12. RAGFlow：深度文档解析、融合召回与可视化引用

## 项目卡片

- GitHub：[infiniflow/ragflow](https://github.com/infiniflow/ragflow)
- 本地源码：`research/source-code/rag/12-ragflow`
- 锁定版本：`5e871986e259`
- 定位：完整 RAG 平台，覆盖文档解析、知识库、检索、Agent、引用与管理界面。
- 一句话判断：RAGFlow 最值得借鉴的是“解析质量是一等公民”，用户能看到块和版面并纠错；但整个平台过重，不适合为 SmileBoss 全量替换现有后端。
- 重要性：P1。

## STAR

### S — Situation

企业文档中的表格、图片、标题、页眉和跨页段落让纯文本抽取失真。若索引端错了，后面的模型再强也无法恢复事实；而黑盒切块让业务人员无法定位召回错误。

### T — Task

提供深度文档理解、可配置模板切块、多策略召回和重排、证据引用、块可视化与人工纠正，并把知识库运营变成可观测流程。

### A — Action

解析层结合版面分析/OCR/VLM 处理 PDF、表格和图片；按文档类型使用模板化 chunking，保存坐标和页面信息。索引层生成向量并记录关键词/元数据。查询端执行多路 recall，融合候选后使用重排模型，生成端严格携带 chunk 来源并在 UI 中展示引用。用户可查看解析块、纠正错误、调整切块与召回配置。

### R — Result

在复杂文档和知识库运营上比简单框架完整，适合从源头诊断“为什么没召回”。代价是组件多、部署和升级复杂、资源消耗大；平台的通用数据模型未必适合招聘领域的强结构事实和合规审计。

## 完整执行流

1. 上传文档，识别类型并进入解析队列。
2. 版面/OCR/VLM 提取文字、表格、图片说明和坐标。
3. 按模板形成块，业务人员可预览和修正。
4. 生成 embedding、关键词和 metadata，写索引。
5. 查询经改写后进入 semantic/full-text/hybrid 等召回器。
6. 过滤、融合、去重和 rerank 得到最终上下文。
7. LLM 生成回答并绑定 chunk/page 引用。
8. UI 展示答案、来源和解析位置；反馈用于调整知识库。

## 难点

| 难点 | 级别 | 做法 | SmileBoss 选择 |
|---|---|---|---|
| 复杂版面 | P1 | OCR/VLM/版面模型 | 简历解析需保留双栏、表格和时间轴 |
| 可纠错性 | P1 | 块可视化 | HR 可修正字段，修改应形成新版本而非覆写原件 |
| 多路检索 | P1 | 召回融合+rerank | 在 Qdrant/搜索层实现同等能力 |
| 平台复杂度 | P2 | 完整微服务 | 不直接引入整套，先抽象关键模式 |
| 领域 Schema | P1 | 通用 chunk | 另建 candidate_fact，不只依赖文本块 |

## SmileBoss 借鉴

实现“简历解析预览”：原 PDF、识别栏目、结构化字段和证据高亮并排显示，HR 修正后触发增量重索引。检索调试页展示每路召回、过滤、RRF、重排分和最终引用。这比增加一个更大模型更能提升运营效率。不要为获得解析 UI 就整体迁移到 RAGFlow。
