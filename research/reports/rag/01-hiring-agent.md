# 01. Hiring Agent：简历结构化证据与公平评分

## 项目卡片

- GitHub：[fatmakahveci/hiring-agent](https://github.com/fatmakahveci/hiring-agent)
- 本地源码：`research/source-code/rag/01-hiring-agent`
- 锁定版本：`70fd3ea9aa74`
- 技术定位：简历解析、候选人证据抽取、岗位适配评分、GitHub 公开信息补强与公平性约束。
- 一句话判断：它不是典型的“向量库问答”项目，但对招聘 RAG 的第一公里最有价值——先把简历变成可信、可比较、可引用的结构化证据，再谈召回和推荐。
- 重要性：P0/P1。解析错误会污染之后所有推荐、面试和评分结论。

## STAR 分析

### S — Situation

原始简历通常是 PDF，版式、栏目和表达差异很大；同一技能可能散落在工作经历、项目和个人简介中。若直接把全文切块并做向量相似度，系统很难回答“候选人在哪个项目中使用过 Java、持续多久、结果如何”，也容易把简历中的提示注入文本当成系统指令。

### T — Task

系统要完成 PDF 结构保留、栏目级事实抽取、字段校验、公开资料补强、证据化岗位评分和偏差检查；中间产物必须可缓存、可审计，不能只留下一个最终分数。

### A — Action

项目先把 PDF 转成尽可能保留标题和列表结构的 Markdown，再按简历栏目调用 LLM，而不是一次把全文交给模型。每个栏目配合 Jinja 模板、Pydantic/JSON Schema 输出约束，得到教育、经历、项目、技能等结构化对象。随后可读取 GitHub 等公开信息形成补充证据，最后按岗位维度产生“分数 + 原因 + 对应事实”，并加入公平性/一致性提示。各阶段 JSON 结果可缓存，失败时不必重跑整个链路。

### R — Result

结果是可追溯的候选人画像而非模糊摘要，适合作为后续 Qdrant 索引和 AI 面试规划的事实源。主要风险是 LLM 评分具有波动、公开资料可能与候选人身份错配、PDF 隐藏文本可能实施提示注入；因此不能把最终评分当自动录用决定。

## 完整执行流程

1. 接收 PDF，记录文件哈希、候选人和解析版本。
2. PDF 转 Markdown，保留标题、列表、日期和链接。
3. 识别简历栏目；缺失栏目产生显式空值，而不是由模型补写。
4. 对每一栏目使用独立提示词和输出 Schema 抽取事实。
5. Pydantic 校验类型、枚举和必填字段；失败时只重试该栏目。
6. 合并为候选人结构化档案，并缓存原文位置到字段的映射。
7. 可选地拉取 GitHub 公开信号，与简历声明分开存放。
8. 按岗位能力维度匹配事实，生成证据化评分和不确定性说明。
9. 做公平性检查：去掉姓名、性别、年龄等非岗位因素，比较脱敏前后结论。
10. 返回结构化档案、证据列表、评分依据和异常告警。

## 核心数据与源码阅读顺序

建议从 README 和主运行脚本开始，再读 PDF/Markdown 转换、Jinja 提示模板、Pydantic 模型、评分与公平性模块。关键数据链是：`PDF -> Markdown -> Section JSON -> Candidate Profile -> Evidence -> Role Score`。中间 JSON 是可回放和回归测试的契约，不应省略。

## 难点与重要性

| 难点 | 级别 | 项目做法 | 残余风险 |
|---|---|---|---|
| 非规则 PDF 解析 | P1 | 转 Markdown 并保留结构 | 双栏、扫描件仍需 OCR/VLM 和人工修正 |
| 事实与推断分离 | P0 | Schema 化栏目抽取 | 模型仍可能把描述推成结论，应保存原文跨度 |
| 提示注入 | P0 | 分阶段处理和验证 | 仍需把简历内容标为不可信数据，禁止触发工具 |
| 评分稳定性 | P1 | 分维度、给证据 | 需固定 rubric、多次校准和人工复核 |
| 公平性 | P0 | 脱敏与公平提示 | 提示词不是合规保证，还需差异影响评估 |

## 对 SmileBoss 的使用建议

- 直接借鉴：栏目级解析、Pydantic 等价的 Java DTO/JSON Schema、原文证据坐标、中间结果缓存、评分证据链。
- 改造后借鉴：GitHub 补强必须取得授权，并将“外部事实”和“候选人声明”分库、分可信度保存。
- 不建议照搬：让一个 LLM 直接输出最终录用分；只用提示词解决公平性；把简历里的 URL 或指令自动执行。
- 推荐落地：在现有 Spring Boot 中建立 `resume_document`、`resume_section`、`candidate_fact`、`evidence_span` 和 `assessment_run`，再将事实单元嵌入 Qdrant。完整度检查和面试追问都读取同一证据层。
