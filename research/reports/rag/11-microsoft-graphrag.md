# 11. Microsoft GraphRAG：实体关系、社区报告与全局问题

## 项目卡片

- GitHub：[microsoft/graphrag](https://github.com/microsoft/graphrag)
- 本地源码：`research/source-code/rag/11-microsoft-graphrag`
- 锁定版本：`e810e63ac143`
- 定位：把非结构化文本索引为实体、关系、声明和社区报告，支持 Global/Local/DRIFT Search。
- 一句话判断：当问题是“整个候选群体有哪些技能结构、哪些岗位族彼此关联”时，GraphRAG 比普通 top-k 块检索更有价值；但它昂贵且不应成为每次推荐的默认路径。
- 重要性：群体洞察 P1，单人推荐多为 P2。

## STAR

### S — Situation

向量检索擅长找与查询相似的局部片段，却难回答跨越大量文档的全局问题，例如“研发候选人中最常见的技能组合与主要缺口是什么”。单纯塞入 top-k 会漏掉分散证据，也无法显式利用人物—技能—项目—公司之间的关系。

### T — Task

从文本提取实体、关系与 claims，构建图并检测社区，为每个社区生成层次化摘要；查询时根据问题选择全局、局部或探索式路径。

### A — Action

索引端先切分 TextUnits，LLM 抽取实体、关系和声明，生成实体/文本向量；图算法进行社区检测，LLM 为各层社区生成 community reports。Global Search 在多个社区报告上执行 map-reduce，聚合全局主题；Local Search 从指定实体出发，联合邻居、关系、文本单元和社区上下文；DRIFT 从局部相关点开始逐步探索更广关系。

### R — Result

系统能把分散事实汇总为群体主题并解释关联路径。主要代价是索引阶段大量 LLM 调用、实体消歧困难、图更新复杂；错误关系和报告摘要会层层传播。招聘领域还存在把候选人互相关联而造成隐私扩散的风险。

## 完整执行流

1. 原始文档 -> TextUnits，并保存来源映射。
2. LLM 从 TextUnit 抽取 entity、relationship、claim。
3. 规范实体名称并做消歧/合并；生成实体描述和向量。
4. 构图并计算社区层级。
5. 为每个社区生成可引用报告，保存统计与来源。
6. 查询分类：全局主题走 community reports；具体实体走 local；探索性问题走 DRIFT。
7. Global：并行 map 社区 -> 产生要点/评分 -> reduce 总结。
8. Local：实体向量定位 -> 扩展邻居/关系/TextUnits -> 生成。
9. 输出结论与来源；索引增量变更时重算受影响子图/社区。

## 难点

| 难点 | 级别 | 项目做法 | 招聘风险 |
|---|---|---|---|
| 实体消歧 | P1 | LLM/规范化后构图 | 同名候选人绝不能合并，必须以内部 ID 为主 |
| 全局聚合 | P1 | 社区报告 map-reduce | 摘要会丢少数群体信息，需保留统计原表 |
| 成本 | P2 | 离线索引 | 只对稳定知识和分析域启用，不处理每次简历更新 |
| 图错误传播 | P1 | 来源映射 | 关系边需置信度、证据和人工修正 |
| 隐私 | P0 | 通用项目不替你解决 | 禁止创建无业务必要的候选人社会关系图 |

## SmileBoss 借鉴

只在三个场景使用图：技能 taxonomy、岗位—技能—题目关系、匿名聚合的人才供需洞察。单候选推荐仍以结构化事实 + 混合 RAG 为主。若构图，节点使用内部稳定 ID，边必须带来源、有效期和租户；群体报告做 k 匿名/最小样本限制。不要照搬“对全部简历抽图并生成社区报告”。

## 评分

架构学习 5/5；生产成熟度 4/5；招聘相关性 3/5；接入成本 1/5；作为高级分析储备，不是一期基座。
