# 14. R2R：多模态、混合检索、知识图谱、引用与访问控制

## 项目卡片

- GitHub：[SciPhi-AI/R2R](https://github.com/SciPhi-AI/R2R)
- 本地源码：`research/source-code/rag/14-r2r`
- 锁定版本：`9c5a94d151f9`
- 定位：面向生产的 RAG/Agent API，覆盖摄取、混合搜索、KG、深度研究、认证和集合。
- 一句话判断：R2R 的价值在于证明检索并非孤立算法，而是与文档生命周期、认证、集合和引用共同组成产品 API。
- 重要性：P0/P1。

## STAR

### S — Situation

生产 RAG 需要处理多格式文件、用户/集合权限、增量更新、搜索、生成和引用；一个 notebook 式向量检索无法解决身份隔离、文档删除和 API 稳定性。

### T — Task

提供从摄取到 Agent 回答的一体化服务：文档解析、向量/关键词混合检索、RRF、知识图谱、引用、用户认证和 collection 级组织。

### A — Action

文档经 ingestion pipeline 解析并写入文档/块/向量存储；搜索可组合 semantic 与 keyword，并用 RRF 融合，也可调用知识图谱。用户和 collection 在服务层限制可检索范围。RAG/Agent 端使用检索结果生成带 citation 的答案，复杂任务进入 research/agent 路径；API 和 SDK 对这些能力统一封装。

### R — Result

生命周期和产品边界完整，便于理解“删除文档必须删除向量、图边和缓存”。但平台很大，直接引入会与 SmileBoss 的 Spring Boot、MySQL、Qdrant 和认证体系重叠；通用 collection 权限也不等于招聘字段级合规。

## 完整执行流

1. 鉴权用户提交文档并指定 collection。
2. 摄取任务解析、切块、提取 metadata/多模态内容。
3. 生成向量并写索引，可选构建图实体/关系。
4. 查询携带用户和 collection scope。
5. 服务层先限制授权范围，再执行 semantic/keyword/KG 检索。
6. RRF/重排组合上下文，生成回答。
7. 引用绑定文档和块；日志记录请求、模型和来源。
8. 文档更新/删除同步清理所有派生资产。

## 难点

| 难点 | 级别 | 做法 | SmileBoss 落点 |
|---|---|---|---|
| 生命周期一致性 | P1 | 统一 ingestion/API | 用 outbox + index job 保证 MySQL/Qdrant 最终一致 |
| 权限 | P0 | auth + collections | 再加 tenant、招聘项目、候选授权和字段级规则 |
| 多路融合 | P1 | hybrid + RRF | 复用在岗位/候选召回 |
| 引用 | P1 | citation | 引用必须能回到简历页码/面试时间点 |
| 平台重叠 | P2 | 全栈服务 | 不整体接入，只复用 API/生命周期模式 |

## SmileBoss 借鉴

为每个派生对象记录 `source_document_id/source_version/index_version`。删除或撤回简历授权时，通过事件删除所有块、向量、缓存和生成报告。检索权限写入服务端 Query Filter，绝不能只在提示词里告诉模型“不要看别的租户”。
