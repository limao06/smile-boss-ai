# 15. KAG：Chunk-Knowledge 双向索引、Schema 对齐与逻辑规划

## 项目卡片

- GitHub：[OpenSPG/KAG](https://github.com/OpenSPG/KAG)
- 本地源码：`research/source-code/rag/15-kag`
- 锁定版本：`fdab15b3929d`
- 定位：知识增强生成，结合文本块、结构知识、Schema 和逻辑形式规划。
- 一句话判断：KAG 适合必须执行关系和数值推理的场景；对 SmileBoss 的最大启发是“结构化招聘知识与原文块互相索引”，而不是立刻引入整套复杂框架。
- 重要性：P1。

## STAR

### S — Situation

普通 RAG 对“某候选最近三年在具备云经验且通过一面的人中排名如何”这类关系、过滤和计算问题不稳定。文本里有证据，但正确答案还需要 Schema、关系路径、集合操作和数值计算。

### T — Task

把原文块与结构化知识共同索引，以领域 Schema 约束实体/关系抽取和对齐；查询转成可执行的逻辑计划，分别调用文本检索、图查询和计算器。

### A — Action

索引阶段形成 chunk-knowledge mutual indexing：文本块保留叙述，知识层记录实体、属性和关系，二者通过来源链接互相回溯。Schema 约束抽取与实体对齐，减少自由图谱的混乱。查询阶段生成逻辑形式/计划，按步骤检索、连接、过滤、计算，再由 LLM 组织答案。

### R — Result

结构化推理、数值和多跳关系更可靠，且可回到原文。代价是 Schema 设计、实体对齐和持续维护非常重；LLM 生成的逻辑计划仍可能错误，招聘数据变化频繁时图与业务库一致性是难点。

## 完整执行流

1. 定义领域 Schema：Candidate、Skill、Experience、Job、InterviewQuestion 等。
2. 文档切块并抽取受 Schema 约束的实体/属性/关系。
3. 实体对齐到已有 ID，建立 chunk ↔ knowledge 双向链接。
4. 保存图、文本索引和来源证据。
5. 查询解析为逻辑计划，识别检索、关系、多跳、过滤和计算步骤。
6. 执行文本/图/数值子任务并累计中间结果。
7. 验证类型、约束和来源，最后生成带证据答案。

## 难点

| 难点 | 级别 | 做法 | 招聘要求 |
|---|---|---|---|
| Schema 设计 | P1 | 领域约束 | 从最小技能/岗位/题目图开始，避免大而全 |
| 实体对齐 | P1/P0 | knowledge alignment | 候选人只能用内部 ID；同名严禁自动合并 |
| 逻辑计划 | P1 | logical form | 用类型系统、白名单算子和执行结果校验 |
| 双存储一致性 | P1 | mutual indexing | MySQL 为事实源，图/向量均为可重建派生层 |
| 维护成本 | P2 | 完整框架 | 二期以后再评估引入 |

## SmileBoss 借鉴

先构建小型“岗位能力图”：岗位族—能力—技能—面试题—评分维度，不把候选人社交信息放图中。简历事实仍在 MySQL，Qdrant 保存可检索证据，图只表达稳定 taxonomy。需要统计和强过滤时走 SQL，不让 LLM在文本中做算术。
