# 02. Resume Screening RAG：多查询、RRF 与 Small-to-Big

## 项目卡片

- GitHub：[RanjitKumar48/Resume-Screening-RAG-Pipeline](https://github.com/RanjitKumar48/Resume-Screening-RAG-Pipeline)
- 本地源码：`research/source-code/rag/02-resume-screening-rag`
- 锁定版本：`7ebf3e6ca72c`
- 技术定位：面向简历筛选的 FAISS 检索流水线。
- 一句话判断：这是最容易读懂的招聘 RAG 召回范例，价值在“多查询 + RRF + 小块命中后回填整份简历”，不是模型本身。
- 重要性：P1。它直接决定候选人是否进入后续重排池。

## STAR 分析

### S — Situation

岗位描述与候选人简历的措辞不一致：岗位写“分布式系统”，简历可能写 Kafka、微服务或高并发；一次查询容易漏召回。同时，单个简历块命中不等于完整简历适配，但把整份简历直接嵌入又会稀释局部强证据。

### T — Task

对岗位要求扩展多种检索表达，从局部块中高召回候选人，再聚合到简历级别，给后续精排一个小而相对完整的候选池。

### A — Action

入库端用递归字符切分器把简历切成约 1024 字符、重叠约 500 的块，以 `all-MiniLM-L6-v2` 生成向量并写入 FAISS，元数据保留申请人 ID。查询端先区分“指定 applicant ID”与“岗位语义检索”；语义检索时由原始问题扩展出 3–4 个变体，分别召回并用 Reciprocal Rank Fusion 合并，公式为 `score += 1 / (rank + k)`，默认 `k=50`。最终依据块元数据回到申请人 ID，读取完整简历，形成约 5 个候选。

### R — Result

多表达召回减少同义词造成的漏检，RRF 避免不同检索列表的绝对分数不可比，small-to-big 让后续模型看到完整上下文。明显问题是 1024/500 的重叠非常大，索引膨胀且相邻块重复投票；FAISS 本地索引也缺少多租户、在线更新和服务化能力。

## 完整执行流程

1. 读取简历文本并附加 applicant ID、来源和文件信息。
2. 递归切分为大重叠块，生成向量，构建 FAISS 索引。
3. 用户提交岗位描述或候选人 ID。
4. 查询分类器判断走精确 ID 路径还是语义路径。
5. 语义路径生成原查询和 3–4 个技能/职责/经验角度的查询。
6. 每个查询独立 top-k 检索，产生有序块列表。
7. RRF 融合：只依赖名次而非原始相似度。
8. 以 applicant ID 去重并累计证据，选择最终候选。
9. 从原始存储回填完整简历，交给后续 LLM 或人工筛选。
10. 输出候选、命中块和融合分；生产实现应再做重排和权限过滤。

## 为什么 RRF 重要

向量相似度、关键词 BM25 分数和不同查询的分数分布不同，直接加权需要反复标定。RRF 只关心名次，工程上更稳。它不判断候选是否真的满足岗位，只提升“多个召回器共同认可的结果”排序，因此之后仍需 Cross-Encoder 或证据级 LLM 重排。

## 难点与重要性

| 难点 | 级别 | 项目做法 | SmileBoss 应增强 |
|---|---|---|---|
| 查询措辞差异 | P1 | LLM 多查询 | 增加技能词典、职级、行业和时间约束查询 |
| 块到简历聚合 | P1 | applicant ID 回填 | 对同一简历设最大贡献块数，防止重复投票 |
| 多列表融合 | P1 | RRF | 融合 dense、BM25、技能精确匹配和行为信号 |
| 切块冗余 | P2 | 500 字符重叠 | 改为栏目/经历原子块，重叠 10%–20% |
| 在线服务 | P1 | 本地 FAISS | 使用现有 Qdrant，添加租户和状态过滤 |

## 对 SmileBoss 的使用建议

- 直接借鉴：查询路由、多查询、RRF、块命中后回填候选人完整画像。
- 改造后借鉴：把 applicant ID 扩展为 `tenant_id + candidate_id + resume_version`；在向量检索前应用租户、隐私授权、求职状态过滤。
- 增加一层：先召回 100 个候选，规则/技能精排到 30，再 Cross-Encoder/LLM 重排到 10；每个结果返回命中经历和缺口。
- 不建议照搬：超大重叠、只用 dense、直接将 top-5 当推荐结果、把完整 PDF 文本无裁剪塞给 LLM。
