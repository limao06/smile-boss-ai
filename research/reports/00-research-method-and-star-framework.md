# 研究方法与 STAR 源码分析框架

## 1. 研究目标

本研究不是制作 GitHub 项目推荐榜，而是回答四个工程问题：

1. RAG 从原始数据进入系统，到最终形成可引用答案，究竟经过哪些阶段？
2. 多 Agent 如何分工、共享状态、交接产物、重试、终止和接受人工干预？
3. Text-to-SQL 如何在大 Schema、业务术语、数据权限、SQL 幻觉和执行安全之间取得平衡？
4. 哪些设计可以复用到 SmileBoss 的简历解析、岗位推荐、AI 面试、完整度评估和活跃度分析？

## 2. 项目选择标准

项目不是只按 Star 数排序，而按五个维度筛选：

| 维度 | 判断方法 | 原因 |
|---|---|---|
| 架构代表性 | 是否代表一种不同路线，如父子块、GraphRAG、混合检索、语义层、工作流图 | 避免 20 个项目只是同一种向量搜索的重复 |
| 源码可解释性 | 能否定位入口、状态结构、检索器、Agent、提示词、评估或执行器 | 只展示产品而无核心源码的项目不适合深度拆解 |
| 与招聘相关性 | 是否处理简历、职位、面试、人才搜索、报告生成或数据分析 | 保证研究结果能落地到 SmileBoss |
| 生产价值 | 是否考虑权限、多租户、审计、连接器、失败恢复、缓存、可观测性 | Demo 的高准确率不等于可上线 |
| 方法互补性 | 是否补足其他项目的盲点 | 形成完整的技术拼图 |

## 3. STAR 在技术项目分析中的定义

传统 STAR 用于描述经历；这里将其改造成系统设计分析框架：

### S — Situation：系统面对的真实情境

说明输入数据、用户、业务约束和失败代价。例如，岗位推荐面对的是“简历短、职位长、技能同义词多、时间信息重要、推荐理由必须可解释”，而不只是“做相似度搜索”。

### T — Task：系统必须完成的责任

描述可验证任务，而非抽象口号。典型任务包括：解析并形成证据、召回候选、裁剪上下文、重排、生成答案、验证事实、给出引用、控制成本、隔离租户。

### A — Action：源码中实际采取的行动

这是报告最重要的部分。按执行时序解释：

```text
入口/API
  -> 输入规范化与权限上下文
  -> 索引或预处理
  -> 查询理解/规划/路由
  -> 检索或工具调用
  -> 融合、重排、扩展、压缩
  -> 生成或执行
  -> 验证/反思/重试
  -> 引用、持久化、观测与返回
```

对于 Agent 项目，还会额外检查：

- Agent 的角色是否只是提示词，还是具有独立状态、工具和权限；
- Agent 间传递的是自由文本还是结构化产物；
- 路由是静态边、LLM 决策、事件订阅还是监督者分派；
- 循环是否有最大次数、预算、终止条件和人工审批；
- 失败后是整体重跑、节点重试、状态回滚还是从检查点恢复。

对于 Text-to-SQL 项目，还会额外检查：

- Schema、列描述、关系、示例值、业务规则和历史问答怎样建立上下文；
- 是否做表/列裁剪与实体值链接；
- 是否生成多个 SQL 候选；
- 是否真实执行、比较结果、修复错误和限制危险语句；
- 是否在生成前应用用户可见范围，而不是生成后再过滤。

### R — Result：结果、价值和残余风险

同时记录四类结果：输出物、准确率/成本收益、适用场景、未解决风险。没有公开基准时不虚构数值，而用“源码具备/不具备”的证据判断成熟度。

## 4. 每份项目报告的固定结构

每份报告都包含：

1. 项目卡片：GitHub、本地源码、锁定提交、技术定位；
2. 一句话判断与重要性；
3. STAR 四段；
4. 从请求到返回的完整执行流程；
5. 关键数据、状态、索引、消息或 SQL 的流向；
6. 核心模块与建议源码阅读顺序；
7. 难点表：难点、重要性、项目做法、残余风险；
8. 设计亮点；
9. 局限与生产风险；
10. SmileBoss 的“直接借鉴 / 改造后借鉴 / 不建议照搬”；
11. 场景化评分。

## 5. “完整执行流程”的证据等级

| 等级 | 证据 | 报告中的表达方式 |
|---|---|---|
| A | 源码入口、类、配置与调用链相互印证 | 明确写“源码执行”并给出路径 |
| B | 官方 README/文档与局部源码相互印证 | 写“官方流程 + 源码模块” |
| C | 论文或架构图说明，但当前仓库仅保留部分实现 | 明确写“论文/官方设计”，不冒充当前代码行为 |
| D | 基于架构的合理推断 | 必须标记为“推断”，不作为事实 |

## 6. 重要性分级

| 级别 | 含义 | 招聘系统例子 |
|---|---|---|
| P0 | 错误会造成越权、歧视、错误录用建议或数据泄露 | 租户隔离、权限过滤、面试偏差审计、SQL 只读控制 |
| P1 | 直接决定召回率、答案可信度或系统可恢复性 | 多路召回、重排、引用、检查点、执行验证 |
| P2 | 主要影响成本、延迟、运营效率和可维护性 | 缓存、批量索引、并发、模型路由、追踪 |
| P3 | 主要影响体验或开发便利性 | UI 展示、低风险的文案润色、配置生成器 |

## 7. 评分口径

采用 1–5 分：

- 架构学习价值：能否提供清晰、可迁移的系统设计；
- 生产成熟度：权限、故障、持久化、部署和观测是否完备；
- 招聘相关性：与简历、岗位、面试、报告或招聘分析的距离；
- 接入成本：5 分表示更容易接入 SmileBoss，1 分表示改造巨大；
- 当前采用建议：优先参考、选择性参考、研究储备或不建议作为基座。

## 8. 研究边界

- 没有运行每个项目的全量模型推理和付费云服务；结论来自锁定提交的静态源码、配置、测试、示例与官方资料。
- GitHub Star 是易变指标，因此报告不以某一天的精确 Star 数作为质量结论。
- 项目的宣称指标只有在官方仓库/论文明确给出时才记录，并与 SmileBoss 的真实招聘数据效果区分开。
- 本研究不是法律意见。简历、面试和用户行为分析涉及个人信息、自动化决策与公平性，正式上线前仍需法务、隐私和人力资源专家复核。
